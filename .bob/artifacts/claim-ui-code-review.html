Security

BUG/SEC Express bound to all interfaces (0.0.0.0)
server/index.mjs · line 466

app.listen(PORT, ...) without a host argument binds to 0.0.0.0, exposing the local server (and the Monday.com API key proxy) to every device on the same network.

Fix: bind explicitly to loopback.

app.listen(PORT, '127.0.0.1', () => { ... });
BUG/SEC CORS wildcard — no origin restriction
server/index.mjs · line 111

app.use(cors()) allows any origin to call your local Monday.com proxy with no restrictions. Combined with the missing host binding above, any page on the LAN can exfiltrate the API key via the /api/config endpoint.

Fix: restrict CORS to localhost origins only in production.

const isProd = !process.env.DEV;
app.use(cors({
  origin: isProd ? ['http://localhost:3001'] : true,
}));

Correctness / Bugs

BUG ACTIVITY_TYPES duplicated between server and client — will diverge
server/index.mjs · lines 31–46  |  src/services/claims.ts · lines 1–16

The same 14-entry enum is copy-pasted in two places. If one is updated the other silently lags behind, producing wrong activity names in the quick-fill template endpoint.

Fix: move the constant to a shared module (e.g. shared/activityTypes.mjs) imported by both. Alternatively expose a /api/activity-types endpoint from the server and consume it on the client.

BUG useEntryForm initial state is stale after editEntry changes
src/hooks/useEntryForm.ts · lines 31–35

The form values are initialised from editEntry once (via the useState lazy initialiser) and never re-synchronised when editEntry changes. If the user edits entry A, closes the modal, then immediately edits entry B, the form still shows entry A's data.

Fix: use a useEffect (or useLayoutEffect) that resets values when editEntry changes:

useEffect(() => {
  if (editEntry) setValues(editEntry);
}, [editEntry?.id]);
BUG useMonthlyL104 silently swallows errors; loading state is never exposed
src/hooks/useData.ts · lines 104–141

The catch handler is an empty lambda .catch(() => {}). A network failure leaves the monthly totals at zero with no indication to the user. The hook also has no loading state, so the summary bar renders 0h while the data is in flight.

Fix: add minimal error and loading states, or at minimum log the error.

BUG GraphQL query-params injection via string interpolation
server/index.mjs · lines 248–257 and 373

User-controlled values (userId, dateFilter) are interpolated directly into the GraphQL query string:

ruleParts.push(`{ column_id: "person", compare_value: ["person-${userId}"], ...}`);

A crafted userId value could close the literal and inject arbitrary GraphQL. The Monday.com API validates queries server-side, but defence-in-depth requires server-side validation of the inputs before interpolation.

Fix: validate userId is an integer and dateFilter entries match /^\d{4}-\d{2}-\d{2}$/ before constructing the query string.

if (!Number.isInteger(Number(userId))) throw new Error('Invalid userId');
dateFilter.forEach(d => {
  if (!/^\d{4}-\d{2}-\d{2}$/.test(d)) throw new Error('Invalid date');
});

Code Quality / Architecture

WARN Month-dates calculation is duplicated verbatim in two views
src/pages/WeekView.tsx · lines 60–73  |  src/pages/ReportView.tsx · lines 48–60

Both views contain identical logic to compute the calendar-grid dates for a month. Extract this to getMonthGridDates(date: Date): Date[] in src/services/claims.ts and import it in both places.

WARN any type on editEntry in WeekView
src/pages/WeekView.tsx · line 86

const [editEntry, setEditEntry] = useState<any>(null) bypasses all type-checking for the form entry. The shape is already well-defined in useEntryForm.ts — use that type directly:

import type { FormValues } from '../hooks/useEntryForm';
const [editEntry, setEditEntry] = useState<({ id: string } & FormValues) | null>(null);
WARN Hardcoded board ID appears in three places
server/index.mjs · line 29  |  src/context/SettingsContext.tsx · line 30  |  README.md

'6500270039' is the default board ID. It is currently defined independently in the server and in the client-side default settings. A single authoritative source (served from /api/config or a shared constant) prevents the two from drifting.

WARN e: any in catch blocks throughout hooks and views
src/hooks/useData.ts · lines 64, 163  |  src/hooks/useEntryForm.ts · lines 79, 91

Typing caught errors as any is a common TypeScript anti-pattern and may hide real typing issues. Use the narrower pattern instead:

} catch (e) {
  const msg = e instanceof Error ? e.message : String(e);
  setError(msg);
}
WARN ReportView re-implements its own data-fetching instead of using useClaims
src/pages/ReportView.tsx · lines 63–85

ReportView duplicates the query + parse + error-state logic that useClaims already encapsulates. Using the existing hook would halve the data-layer code in this file, and the queryDates / month-view logic would consolidate with the WeekView refactor above.

WARN setTimeout(() => refresh(), 600) is a fragile workaround
src/pages/WeekView.tsx · line 111

The 600ms delay is inserted to give Monday.com time to index new items before re-querying. This is not reliable on slow connections and will feel laggy on fast ones. A better approach is optimistic UI (add the item to local state immediately from the form values) with a background refresh to reconcile.

UX / Accessibility

WARN Several strings are hard-coded English, bypassing i18n
src/pages/WeekView.tsx · lines 225, 232, 237  |  src/pages/PresalesView.tsx · lines 165–166  |  src/pages/SettingsView.tsx · many

Strings like "Week view", "Month view", "Hide weekends", "No opportunities match the filter", and most of SettingsView are plain English literals rather than t('...') calls. This breaks the Italian translation for any user who has selected it.

WARN Month-view detail panel is keyboard-inaccessible
src/pages/WeekView.tsx · line 292–294

Day tiles in month view open the detail panel via an onClick on a <Tile>, which renders as a <div>. There is no role="button", no tabIndex, and no onKeyDown handler, making this feature unreachable by keyboard users.

// Add to the month-view Tile:
role="button"
tabIndex={0}
onKeyDown={(e) => { if (e.key === 'Enter' || e.key === ' ') setSelectedDayDetail(dateStr); }}
WARN PWA install button dispatches a non-standard synthetic event
src/pages/SettingsView.tsx · lines 217–220

The "Add to Dock" button fires new Event('beforeinstallprompt') — this has no effect. The browser-controlled prompt must be captured and deferred in a window.addEventListener('beforeinstallprompt', ...) handler and then called via prompt(). Without this the button silently does nothing.

WARN InlineNotification error in EntryFormModal has a no-op onClose
src/components/EntryFormModal.tsx · line 89

onClose={() => {}} — the user can click the X on the notification but nothing happens; the error stays visible. The parent provides the error state so the close handler needs to clear it via a new onClearError prop (or expose setError from the hook).

Strengths

GOOD Clean separation: Express proxy keeps the API key server-side

The Monday.com API key never touches the browser bundle. All mutations go through the Express layer. This is the right architecture for a local desktop tool of this kind.

GOOD Solid test coverage for the service layer

43 tests across all public functions in claims.ts and the full api.ts surface. Edge cases (missing columns, no date, unknown activity value) are explicitly covered.

GOOD Hooks are well-factored and reusable

useWeekNavigation, useClaims, useEntryForm, and useRecentTemplates are each focused on one concern and composable. The pattern is consistent and easy to extend.

GOOD Cross-platform config path handling

macOS / Linux / Windows paths are derived at startup from os.platform() with a sensible fallback. The config is shared with the TUI without coupling the two processes at runtime.

GOOD API key validation before saving

The POST /api/config endpoint calls Monday.com with the new key before persisting it. This prevents saving obviously wrong keys.

GOOD Keyboard shortcuts with correct input guard

The keydown handler in WeekView correctly short-circuits when the active element is an input or textarea, preventing navigation shortcuts from firing while typing.
